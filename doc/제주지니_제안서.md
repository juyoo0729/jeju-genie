## 1. 어떤 문제를 푸는가

### 1.1 도메인: 제주 여행·생활 정보

제주는 연간 1천만 명 이상이 찾는 국내 최대 관광지이지만, 정보는 심하게 파편화되어 있다.

- 관광지·축제 정보는 제주관광공사(비짓제주)에,
- 맛집·숙소 후기는 블로그와 지도 앱에,
- 유가·교통·날씨 같은 생활 정보는 각각 오피넷·ITS·기상청에,
- 역사·문화·방언 같은 배경 지식은 도청 자료와 백과에 흩어져 있다.

사용자는 검색을 여러 번 반복하고도 "그래서 내 상황에서 뭘 하면 되는데?"라는
질문의 답을 얻지 못한다.

### 1.2 왜 일반 LLM 챗봇으로는 안 되는가

| 한계 | 내용 |
|---|---|
| 환각 | 일반 LLM은 제주 세부 정보(영업시간·좌표·요금·폐업 여부)를 그럴듯하게 지어낸다 |
| 최신성 | 오늘의 유가, 지금의 날씨, 이달의 축제는 학습 데이터에 존재하지 않는다 |
| 근거 부재 | 답변의 출처를 확인할 방법이 없어 신뢰할 수 없다 |

## 2. 누구를 위해 푸는가

| 사용자 | 핵심 니즈 | 제주 지니의 대응 |
|---|---|---|

| 제주 도민 | 유가·교통·전기차 충전 등 생활 정보 | 실시간 API 조회, 최저가 주유소 지도 링크 |
| 외국인 방문객 | 언어 장벽 | 영어 질문 시 영어로 응대 |

## 3. 어떻게 푸는가

### 3.1 핵심 아이디어: 데이터의 폭이 답변의 상한을 결정한다

같은 LLM이라도 접근 가능한 데이터의 폭이 답변 품질의 상한을 결정한다.
그래서 모델 크기 대신 **데이터 확보에 투자**한다:

- 공공데이터포털 '제주' 검색 결과 **417개 API 전수 조사 → 397개 이상 활용신청·발급**
- 정적 지식(역사·관광지·문화)은 **RAG 벡터 색인(2,936청크)** 으로,
- 시점성 데이터(날씨·유가·교통·통계)는 **질의 시점 실시간 도구(11종)** 로 분리

"바뀌지 않는 것은 색인하고, 바뀌는 것은 그때 조회한다" — 신선도 문제를 구조로 해결한다.

### 3.2 시스템 구성

```
사용자 (React SPA, SSE 스트리밍 채팅 + 지도 + 실시간 사이드바)
   │
FastAPI 백엔드 — 스트리밍 tool-calling 에이전트 루프 (gpt-5-mini)
   ├─ search_jeju_knowledge : Chroma 벡터 검색 (RAG, 2,936청크, GCS 동기화)
   ├─ 실시간 도구 10종     : 날씨·유가·교통·충전소·좌표·통계·방언·관광검색·위키
   └─ 답변 계약            : 출처 1개 이상 필수 + 장소 답변엔 지도 마커 필수
   │
GCP — Cloud Run(서울) + Artifact Registry + GCS
CI/CD — GitHub Actions: push → lint/pytest → build → 자동 배포
```

### 3.3 신뢰성 설계 (기본 모델과의 차별점)

1. **모든 답변에 출처**: 도구가 참조한 원문 URL을 출처 칩으로 강제 표시. 출처가 없으면
   검색 링크로 폴백 — 빈 출처는 시스템이 허용하지 않는다.
2. **실시간 수치 인용**: 유가·날씨는 "지금 기준" 수치로 답하고 실시간 데이터 배지로 표시.
3. **지어내기 금지**: 도구가 없는 영역(일기예보·항공편)은 수치 생성을 금지하고
   확인 안내로 답한다. 자신감과 환각을 구분한다.
4. **도메인 가드**: 제주와 무관한 질문은 정중히 거절하고 제주로 화제를 전환한다.

### 3.4 서비스 견고성·보안 원칙

- **폴백 계층**: LLM 장애 시 로컬 모델 → 안내 응답, 도구 실패 시 일반 지식으로 답변 유지,
  상류 데이터 장애 시 스냅샷 폴백. 부분이 죽어도 전체는 살아 있다.
- **배포 안전**: 테스트(pytest)가 CI 배포 게이트 — 깨진 코드는 프로덕션에 도달 불가.
  Cloud Run 리비전 단위 즉시 롤백.
- **키 보안**: 코드·저장소·이미지에 API 키 미포함 (.env gitignore + GitHub Secrets +
  Cloud Run 환경변수 주입). 서버에 사용자 DB 없음 — 대화 기록은 브라우저에만 저장.

## 4. 개발 범위와 일정 (해커톤 기간 약 4일)

| 단계 | 내용 |
|---|---|
| 1. 데이터 확보 | 공공 API 417개 조사, 397+ 발급, 키·엔드포인트 엑셀 정리 |
| 2. 코어 구축 | FastAPI + RAG(Chroma) + React 채팅 UI + Docker/Cloud Run/CI-CD |
| 3. 에이전트 전환 | 스트리밍 tool-calling 루프, 실시간 도구 11종, 지도·출처 계약 |
| 4. 품질 라운드 | 사용자 피드백 기반 개선 사이클 반복 (시도·실패·개선 기록) |
| 5. 발표 준비 | 순위 추천·지도 필수화·출처 강화, 발표자료·산출물 정리 |

## 5. 기대 효과와 확장성

- **즉시 효과**: 제주에 관한 질문 하나로 지식 + 실시간 수치 + 지도 + 출처를 한 번에 제공
- **확장 구조**: 데이터 소스는 커넥터/도구 파일 하나 추가로 늘어난다 (코어 무수정) —
  재난안전 API 6종은 serviceId·키까지 확보 완료, 승인 대기 중인 기상청 예보·항공편도
  승인 즉시 도구로 편입 가능
- **복제 가능성**: 도메인 특화 구조라 "부산 지니", "강릉 지니" 등 타 지역 복제가
  데이터 교체 수준으로 가능
