### 슬라이드 4 — 문제 정의 (1:30)

**어떤 문제를 누구를 위해 푸는가.**

제주는 연간 1천만 명 이상이 찾는 곳인데, 정보는 관광공사 따로, 블로그 따로,
유가 앱 따로, 날씨 앱 따로 흩어져 있습니다. 여행자는 검색을 열 번 하고도
"그래서 뭘 하지?"의 답을 못 얻고, 도민은 유가나 교통 같은 생활 정보를 매번 딴 데서 찾습니다.

"그럼 ChatGPT에 물어보면 되지 않나?" — 안 됩니다. 두 가지 이유 때문입니다.

- 첫째, **환각**. 일반 LLM은 제주 세부 정보 — 영업시간, 좌표, 요금 — 를 그럴듯하게 지어냅니다.
- 둘째, **최신성**. 오늘의 유가, 지금의 날씨는 학습 데이터에 없습니다.

저희 접근은 명확합니다. **바뀌지 않는 지식은 RAG로, 바뀌는 수치는 실시간 API 도구로.**
그리고 소스가 계속 늘어나야 하니 **플러그인 구조**로 시작부터 설계했습니다.

### 슬라이드 5 — 솔루션 개요 (1:00)

그래서 만든 게 제주 지니입니다. 세 기둥입니다.

- **근거 기반**: 답변마다 출처 칩이 붙습니다. 출처 없는 답변은 시스템이 허용하지 않습니다.
- **실시간**: 날씨·유가·교통을 질문 시점에 조회해서 "지금 기준" 수치로 인용합니다.
- **운영 가능**: 데모가 아니라 Cloud Run에 배포된 라이브 서비스이고, 커밋 한 번이 곧 배포입니다.

사용자 경험도 챙겼습니다. 답변은 스트리밍으로 흐르고, 장소 추천은 **3~5곳을 순위로** 제시하며
**지도가 함께** 뜨고, 상태에 따라 마스코트가 바뀝니다.

### 슬라이드 6 — 숫자로 보는 제주 지니 (1:30) ★ 물량전 슬라이드

여기가 저희가 가장 자신 있는 부분입니다. **저희는 데이터 물량으로 승부합니다.**

공공데이터포털에서 '제주'로 검색되는 API **417개를 전수 조사**했고,
그중 **397개 이상을 실제로 활용신청·발급**받았습니다. 자동승인은 물론이고,
심의형 API는 신청 폼 구조를 분석해서 발급까지 뚫었습니다. 이 과정 전체가 엑셀에 기록돼 있습니다.

이렇게 확보한 데이터가 서비스에 이렇게 들어가 있습니다.
- 정적 지식은 **2,936건**으로 벡터 색인 — 관광지 1,700여 건, 도정·문화·방언 1,100여 건.
- 실시간은 **도구 11종** — 교통은 관측 구간 **1만 2천여 개**, 유동인구는 읍면동 43곳 좌표 매핑.

핵심 메시지는 이겁니다. **같은 gpt-5-mini라도, 접근할 수 있는 데이터의 폭이 답변의 상한을 결정합니다.**
제주에 관한 한, 저희가 그 폭을 최대로 확보했습니다.

### 슬라이드 8 — 모델 설계 1 (1:30)

모델 이야기를 하겠습니다. **왜 gpt-5-mini인가.**

- 데모 트래픽에 대형 모델은 과합니다. mini급이면 한국어 품질이 충분하고 비용·지연이 맞습니다.
- 단, **함수호출과 스트리밍을 동시에** 지원해야 했습니다. 도구 11종 결합의 전제 조건입니다.
- 그리고 추론 모델이라 **reasoning effort를 low로** 실측 튜닝했습니다. 이 얘기는 다음 슬라이드에서 더 합니다.

설계에서 강조하고 싶은 결정이 두 개입니다.

첫째, **RAG를 '도구'로 편입**했습니다. 처음엔 모든 질문에 검색을 강제했는데,
그러면 "안녕하세요" 같은 잡담에도 검색이 돌아서 느립니다. 지금은 모델이
필요할 때만 `search_jeju_knowledge` 도구를 호출합니다.

둘째, **3단계 파이프라인을 단일 스트리밍 루프로** 갈아엎었습니다.
원래는 RAG 검색 → 도구 선택 호출 → 답변 스트리밍, LLM 왕복이 3번이었는데
지금은 1번입니다. 도구가 필요 없으면 첫 왕복에서 바로 토큰이 흘러나옵니다.

[다음 장]

### 슬라이드 9 — 모델 설계 2: RAG 파이프라인 (1:00)

데이터가 색인되는 과정입니다. 발급받은 API에서 커넥터 5종이 데이터를 가져오고 —
**커넥터는 파일 하나 추가하면 소스가 하나 늘어나는 플러그인**입니다 —
정제와 노이즈 필터를 거쳐 OpenAI 임베딩으로 Chroma에 들어갑니다.

설계 결정 하나만 짚겠습니다. **컬렉션을 임베딩 모델별로 분리**했습니다.
`jeju-프로바이더-모델` 네이밍이라, 임베딩 모델을 바꾸면 벡터 공간이 섞이지 않고
컬렉션 단위로 재구축·롤백이 됩니다. 모델 버전과 데이터 파이프라인을 함께 관리하는 거죠.

[다음 장]

### 슬라이드 10 — 왜 RAG인가 (1:00) ★ 심사 포인트

"왜 하필 RAG였나"에 답하겠습니다. 후보는 세 가지였습니다.

- **파인튜닝** — 제주 데이터가 계속 바뀌는데 그때마다 재학습해야 하고, 무엇보다
  답변의 **출처를 추적할 수 없습니다.** 근거 기반이라는 저희 핵심 가치와 맞지 않아 제외했습니다.
- **롱컨텍스트** — 자료 전체를 프롬프트에 넣는 방식인데, 저희 데이터는 2,936청크입니다.
  매 질문마다 그걸 전부 보내면 토큰 비용과 지연이 폭발합니다. 제외.
- 그래서 **RAG**입니다. 질문과 유사한 청크만 골라 주입하니 mini급 모델로도 정확도가
  나오고, 출처가 추적되고, 데이터 갱신은 재색인 한 번이면 끝납니다.

실제 흐름을 보시면 — "제주 4.3 사건이 뭐야?"라고 물으면, 모델이 지식 검색 도구를
선택하고, Chroma에서 임베딩 유사도로 관련 청크를 찾고, 그 근거와 출처 메타데이터가
답변과 출처 칩으로 이어집니다.

그리고 역할 분리 — **역사·문화·방언·관광지 상세 같은 정적 지식은 RAG가,
유가·날씨처럼 변하는 수치는 실시간 도구가** 담당합니다. 이 경계 덕분에
RAG 인덱스는 낡을 걱정이 없고, 실시간 수치는 항상 신선합니다.

[다음 장]

### 슬라이드 11 — 실시간 도구 11종 (0:40, 밀리면 압축)

도구 목록입니다. 날씨, 유가, 교통, 전기차, 좌표, 통계, 방언, 관광 검색, 위키, RAG까지.
LLM이 질문을 보고 **스스로 필요한 도구를 골라 병렬로 호출**합니다.

포인트는 아래 한 줄입니다. 각 도구는 출처(refs)와 지도 마커(map_points)를 계약으로 남기고,
에이전트가 그걸 회수해서 화면의 출처 칩과 지도로 보냅니다. **출처와 지도가 우연이 아니라 계약**입니다.

[다음 장]

### 슬라이드 12 — 시도·실패·개선 (1:30) ★ 심사 포인트

솔직하게 실패담을 보여드리겠습니다. 이 표가 저희 작업 내역의 요약입니다.

세 개만 골라 말씀드리면 —

- **답변이 중간에 잘리던 문제.** gpt-5-mini는 추론 모델이라 생각하는 토큰이
  답변 토큰 예산을 잠식합니다. max_completion_tokens를 4배로 늘리고 추론 강도를 low로 내려 해결했습니다.
- **배포하면 LLM이 자꾸 폴백으로 떨어지던 문제.** 원인은 CI가 환경변수를 전체 치환하면서
  수동 주입한 키를 지워버린 거였습니다. 병합 방식으로 워크플로를 고쳐 근본 해결했습니다.
- **"서귀포 찜질방"처럼 지역명+업종 질의에서 지도가 안 뜨던 문제.** 지오코딩 API가
  조합 질의를 못 찾는 걸 실측으로 확인하고, 지역어를 떼고 재시도하는 로직을 넣었습니다.
  이건 발표 준비 중인 **오늘 아침에 고쳐서 배포한** 개선입니다.

**증상 → 원인 분석 → 구조적 해결**, 이 사이클을 아홉 번 돌린 기록입니다.

[다음 장]

### 슬라이드 13 — 신뢰성: 기본 모델 대비 (1:30) ★ 심사 포인트

**그래서 기본 모델보다 뭐가 나은가.** 같은 질문 네 개로 비교했습니다.

- "지금 제주 기름값?" — 기본 모델은 학습 시점 추정치를 말합니다. 제주 지니는
  **오피넷 실시간 도 평균가를 인용하고 출처 칩을 답니다.**
- "호텔 추천" — 기본 모델은 폐업 여부도 모르는 일반 지식 목록. 저희는
  관광공사 최신 DB에서 검색해 **순위 3~5곳 + 지도 + 원문 링크**로 답합니다.
- 그리고 제일 중요한 세 번째 줄 — "내일 날씨"처럼 **도구가 없는 영역은 수치를 지어내지 않습니다.**
  현재 관측값과 확인 안내로 답하도록 강제했습니다. 자신감과 환각을 구분하는 정책입니다.

정량적으로는 pytest 81개가 배포 게이트로 상시 돌고, E2E 시나리오 검증을 거쳤습니다.
정성적으로는 **모든 답변에 출처 1개 이상**이 시스템 레벨에서 강제됩니다.

[다음 장]

### 슬라이드 14 — 서비스 견고성 (1:00)

서비스로서의 견고함입니다. 원칙은 하나 — **부분이 죽어도 전체는 살아야 한다.**

- LLM이 죽으면 로컬 모델로, 그것도 없으면 안내 응답으로.
- 도구 하나가 실패해도 루프는 계속 — 일반 지식으로 답변은 나갑니다.
- 밀집 지도의 상류 API가 GCP에서만 죽는 장애가 실제로 있었는데, 스냅샷 폴백으로 견디고
  상류가 복구되면 자동으로 돌아옵니다. **실장애에서 검증된 폴백**입니다.

비용도 견고성의 일부입니다. min-instances 0이라 유휴 과금이 없고,
캐시 계층으로 외부 API 호출량을 통제합니다.

[다음 장]

### 슬라이드 15 — 보안 (1:00) ★ 심사 포인트

보안입니다. 저희는 API 키가 397종 규모라 **키 관리가 곧 생존**이었습니다.

원칙은 "**코드에 키가 없다**"입니다. 로컬은 .env 하나로 중앙화하고 gitignore,
CI는 GitHub Secrets, 런타임은 Cloud Run 환경변수 주입입니다.
저장소를 통째로 열어봐도 키가 한 글자도 없고, README에는 .env.example 틀만 있습니다.

사용자 쪽으로는 — 서버에 사용자 DB가 아예 없습니다. 대화 기록은 브라우저 localStorage에만 있고,
시스템 프롬프트가 역할을 고정해서 비제주 요청이나 역할 변경 시도는 거절 후 화제를 돌립니다.

[다음 장]

### 슬라이드 16 — MLOps (0:40, 밀리면 압축)

운영 파이프라인 요약입니다. **push 한 번 = 테스트 + 빌드 + 배포.**
오늘 발표 준비 중에도 이 파이프라인으로 당일 여러 차례 배포했습니다.

## Q&A 대비 (10분) — 예상 질문과 답변

**Q1. 왜 gpt-5-mini인가? 더 큰 모델을 쓰면 되지 않나?**
> 저희 병목은 모델 크기가 아니라 데이터 접근이었습니다. 유가·날씨·최신 관광 정보는
> 어떤 크기의 모델도 학습만으로는 모릅니다. 그래서 예산을 모델이 아니라 데이터 폭(API 397종)에
> 투자했고, mini급으로도 도구·RAG 결합으로 충분한 품질이 나옵니다. 비용·지연도 서비스에 맞습니다.

**Q2. RAG 성능은 어떻게 평가했나?**
> 정량으로는 pytest 81개(도구 파싱·에이전트 루프·API 계약)와 E2E 시나리오 검증,
> 정성으로는 실질문 세트로 기본 모델과 비교했습니다(슬라이드 12). 자동화된 답변 품질 평가
> (LLM-as-judge)는 로드맵에 있습니다 — 솔직히 다음 단계입니다.

**Q3. 환각을 완전히 막을 수 있나?**
> 완전히는 못 막습니다. 저희 정책은 세 겹입니다 — (1) 근거를 도구로 확보하고,
> (2) 도구가 없는 영역(예보 등)은 수치 생성을 프롬프트로 금지하고, (3) 변동 정보에는
> 확인 안내를 붙입니다. 그리고 모든 답변에 출처를 강제해 사용자가 검증할 수 있게 합니다.

**Q4. 출처 칩은 어떻게 만들어지나?**
> 각 도구가 실행되면서 자기가 참조한 원문 URL을 refs로 남기고, 에이전트가 회수해
> sources 이벤트로 내보냅니다.
> 출처가 하나도 없으면 질문 기반 검색 링크로 폴백합니다 — 빈 출처는 시스템이 허용하지 않습니다.

**Q5. 트래픽이 몰리면?**
> Cloud Run이 리퀘스트 기반 오토스케일링을 합니다(현재 max 2, 조정 가능).
> 콜드스타트가 이슈면 min-instances를 올리면 되고, 외부 API 호출은 캐시 계층(5~30분)이 흡수합니다.
> 상류 API 쿼터가 실제 병목인데, 소스가 여러 개라 분산됩니다.

**Q6. 데이터 신선도는? 색인이 낡으면?**
> 실시간성이 필요한 데이터는 애초에 색인하지 않고 도구로 뺐습니다. 정적 지식은
> `ingest --reset --push` 한 번으로 재색인되고, 스케줄드 재색인(Airflow)이 로드맵에 있습니다.

**Q7. 임베딩/LLM 모델을 바꾸면?**
> 컬렉션이 모델별로 격리돼 있어 섞이지 않습니다. 새 컬렉션으로 재색인하고,
> 문제가 생기면 이전 컬렉션으로 롤백합니다. LLM은 프로바이더 추상화 계층이 있어
> OpenAI/Ollama가 이미 교체 가능합니다.

**Q8. 키가 유출되면 어떻게 되나?**
> 코드·이미지·저장소에 키가 없어서 유출 경로가 좁습니다. 만약 유출되면 각 포털에서
> 키 재발급 후 Cloud Run 환경변수만 갈아끼우면 됩니다 — 코드 변경·재빌드가 필요 없습니다.
> 공공 데이터 키라 과금 위험도 제한적입니다.

**Q9. 사용자 입력으로 프롬프트 인젝션이 되지 않나?**
> 시스템 프롬프트가 역할과 도메인을 고정하고, 비제주·역할변경 요청은 거절하도록 훈련된
> 페르소나입니다. 도구 인자는 JSON 파싱 실패 시 빈 인자로 안전 처리되고, 도구 자체가
> 읽기 전용(조회성 API)이라 인젝션이 성공해도 파괴적 행동이 불가능합니다.

**Q10. 수익 모델 / 실서비스 계획은?**
> 해커톤 범위는 기술 실증까지입니다. 다만 구조상 지자체 관광 챗봇, 숙박·맛집 제휴,
> B2B 데이터 대시보드로 확장 가능하고, 커넥터 구조 덕에 다른 지역 복제(부산 지니 등)도
> 파일 추가 수준입니다.

**Q11. 개발 중 가장 어려웠던 점은?**
> 두 가지입니다. 첫째, API 발급 자체 — 417개를 조사해 신청 폼·인증 구조가 제각각인
> 포털들을 뚫는 것. 둘째, 추론 모델 특성 — 답변 잘림의 원인이 추론 토큰 잠식이라는 걸
> 찾는 데 시간이 걸렸습니다. 둘 다 작업 내역에 기록돼 있습니다.

**Q12. 지도에 안 뜨는 장소가 있던데?**
> 지오코딩 API가 못 찾는 상호가 있습니다. 오늘 아침 지역어 제거 재시도를 배포해 커버리지를
> 올렸고, 그래도 못 찾으면 마커 없이 답변은 정상 제공됩니다 — 지도는 부가 정보지
> 답변을 막는 요소가 아니게 설계했습니다.
